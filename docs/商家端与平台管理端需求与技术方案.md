# 商家端小程序 + 平台管理端 需求单与技术框架

> 版本：v1.0（待审核）
> 日期：2026-10-21
> 依据：现有用户端功能（美食城浏览、搜索、跨档口购物车与拆单、模拟支付、地址、优惠券、收藏、评价、再来一单）
> 已确认：平台端采用 Vue3 + Element Plus 独立 Web；管理员独立 admin 表；本期覆盖商家端与平台端全部四组功能；支付继续模拟。

---

## 一、现状盘点

### 1.1 已具备

| 端 | 能力 | 代码位置 |
|---|---|---|
| 用户端 | 美食城/档口浏览、搜索、购物车上划弹层、跨档口拆单、模拟支付、地址选择、优惠券领取与抵扣、收藏、评价、再来一单、档口评价展示 | `miniprogram-user/` |
| 商家端 | 工作台、订单列表与状态流转（接单/配送/完成）、菜品与分类管理、档口设置、评价查看、今日统计 | `miniprogram-merchant/` |
| 后端 | 用户/商家 JWT、浏览、购物车拆单、订单、支付（模拟）、优惠券、收藏、评价、文件上传、商家工作台接口 | `src/main/java/...` |

### 1.2 缺口（本期要补）

| 端 | 缺口 |
|---|---|
| 商家端 | 订单详情、拒单/退款、新订单语音提醒、结算账单、菜品规格（`dish_spec` 表已建但未启用）、商家自建店铺券、评价回复、入驻申请（现为自助绑定档口） |
| 平台端 | **完全不存在**：无 admin 表、无管理员登录、无管理接口、无 Web 页面、无抽佣结算、无平台看板 |
| 权限 | `/auth/login` 的角色由客户端传入，任何人可申请 role=2 并自助绑定空档口，存在越权抢绑风险 |

### 1.3 关键结论

本期不是"从零做商家端"，而是**补齐商家端交易闭环 + 从零建立平台管理端 + 修正角色权限模型**。

## 二、角色与权限模型

| role | 身份 | 登录方式 | 可访问 |
|---|---|---|---|
| 1 | 用户 | 微信 code2session | 用户端全部接口 |
| 2 | 商家 | 微信 code2session（需平台审核通过） | 仅本档口的 `/merchant/**` |
| 3 | 平台管理员（新增） | admin 账号 + 密码 | `/admin/**` |

规则（全部为硬约束）：

1. `admin` 表独立，不复用 `user` 表；密码使用 JDK 内置 `PBKDF2WithHmacSHA256 + 16 字节随机盐` 存储，禁止明文、禁止 MD5。
2. 管理员登录接口 `POST /admin/auth/login` 加入白名单，其余 `/admin/**` 必须携带 role=3 令牌。
3. 商家端 `/auth/login` 仍允许客户端声明 role=2（用于区分入口），但**绑定档口必须经平台审核**：
   - 新增 `merchant_apply` 入驻申请表；
   - 商家端下掉"自助绑定档口"，改为"提交入驻申请 / 查看审核进度"；
   - 平台审核通过后才写 `shop.merchant_user_id`，未绑定账号访问业务接口返回 403。
4. 商家端所有查询/写入必须带 `shop_id = 当前商家绑定档口`，禁止跨档口。
5. 平台接口统一在 Service 层调用 `AdminGuard.requireAdmin()`（与现有 `requireMerchantRole()` 风格一致，不引入 Spring Security）。

## 三、功能需求单

### 3.1 商家端（M 系列）

#### M1 订单详情与拒单退款

| 编号 | 需求 | 规则 | 验收 |
|---|---|---|---|
| M1-1 | 订单详情页 | 展示菜品明细（含规格）、地址快照、备注、优惠、实付、下单/支付时间、状态时间轴 | 从订单列表进入，数据与列表一致 |
| M1-2 | 拒单 | 仅 status=1 可拒单，必填原因（下拉+补充），状态 1→5，同时触发模拟退款与退券 | 拒单后用户端订单变"已取消"，券回到未使用 |
| M1-3 | 退款审批 | 用户申请退款后生成退款单，商家可同意/拒绝（必填理由）；同意后订单 6 退款中 → 7 已退款，支付状态更新 | 商家端退款列表可见，用户端状态同步 |
| M1-4 | 状态时间轴 | `orders` 增加 `accept_time/prepare_time/deliver_time/finish_time/cancel_time`（缺失则补） | 详情页时间轴完整 |

#### M2 新订单语音提醒

| 编号 | 需求 | 规则 | 验收 |
|---|---|---|---|
| M2-1 | 新订单轮询 | 工作台每 20s 拉取待接单数量，数量增加时提醒（页面隐藏时停止） | 新订单 20s 内提醒 |
| M2-2 | 语音+震动 | `wx.createInnerAudioContext` 播放本地提示音 + `wx.vibrateLong()`；无音频文件时降级为震动+系统提示 | 真机可听到/感知提醒 |
| M2-3 | 开关 | 提醒开关存 `storage`，默认开启；"我的"页可关闭 | 关闭后不再响铃 |

> 待你提供：提示音 mp3（放 `miniprogram-merchant/assets/order.mp3`）；未提供则用震动+提示音降级方案。

#### M3 结算账单

| 编号 | 需求 | 规则 | 验收 |
|---|---|---|---|
| M3-1 | 账单汇总 | 今日/近7天/本月：订单数、商品金额、配送费、平台抽佣、应结金额 | 与平台结算单金额一致 |
| M3-2 | 账单明细 | 按订单列出：订单号、完成时间、实付、抽佣比例、抽佣金额、应结 | 可关联到订单详情 |
| M3-3 | 结算单只读 | 展示平台生成的结算单（周期、状态、打款时间） | 与平台端结算数据一致 |

抽佣口径：`抽佣基数 = 商品金额 - 平台券分摊金额`；配送费 100% 归商家；店铺券成本由商家承担。比例取 `shop.commission_rate`，为空时取平台默认值。

#### M4 菜品规格

| 编号 | 需求 | 规则 | 验收 |
|---|---|---|---|
| M4-1 | 规格管理 | 菜品编辑页维护规格（名称/加价/排序），启用已有 `dish_spec` 表，增加 `sort/status` 字段 | 可增删改，随菜品保存 |
| M4-2 | 用户端选择 | 有规格的菜品点"+"弹出规格选择，必选一个；无规格直接加购 | 购物车显示"菜名·规格" |
| M4-3 | 订单落库 | `order_item` 增加 `spec_id/spec_name/spec_price`，单价 = 菜品价 + 规格加价 | 订单详情、商家端、账单金额一致 |
| M4-4 | 购物车去重 | 同一菜品不同规格视为不同条目 | 加购/减购正确 |

#### M5 店铺优惠券

| 编号 | 需求 | 规则 | 验收 |
|---|---|---|---|
| M5-1 | 券管理 | 商家创建/停用店铺券：满减/折扣、门槛、发行量、有效期 | 列表、状态切换正常 |
| M5-2 | 用户端同池展示 | 用户领券中心同时展示平台券与店铺券，已领标记；店铺券仅本档口可用 | 领取/使用规则正确 |
| M5-3 | 叠加规则 | 一笔订单只能使用 1 张券（与现状一致），店铺券与平台券互斥 | 结算页只可选 1 张 |

#### M6 评价回复

| 编号 | 需求 | 规则 | 验收 |
|---|---|---|---|
| M6-1 | 回复评价 | 每条评价可回复 1 次，≤200 字；回复后用户端档口评价弹层展示"商家回复" | 用户端可见 |
| M6-2 | 差评标记 | 1–2 星标红并置顶 | 列表排序正确 |
| M6-3 | 平台介入 | 商家回复后平台仍可隐藏违规评价（见 A8） | 隐藏后用户端不展示 |

#### M7 入驻申请（替换自助绑定）

| 编号 | 需求 | 规则 | 验收 |
|---|---|---|---|
| M7-1 | 提交申请 | 档口名、所属美食城、联系人、手机号、营业执照图、营业时间 | 提交后状态"审核中" |
| M7-2 | 进度查询 | 待审/通过/驳回（含驳回原因） | 通过后自动进入工作台 |
| M7-3 | 兼容 | 已绑定档口（如测试账号）不受影响 | 老账号正常使用 |

### 3.2 平台管理端（A 系列）

页面清单（Vue 路由）：

| 路由 | 页面 | 功能 |

| `/order` | 订单监控 | 全平台订单多条件查询、详情、强制取消并退款 |
| `/coupon` | 平台券管理 | 券模板 CRUD、发行量、领取/核销统计 |

后台功能规则：

| 编号 | 需求 | 规则 | 验收 |
|---|---|---|---|
| A1 | 管理员登录 | 账号+密码，连续 5 次失败锁定 10 分钟（Redis 计数） | 错误密码返回统一提示，不区分账号是否存在 |
| A2 | 看板 | 统计口径与商家端一致；金额保留 2 位；日期按 Asia/Shanghai | 与数据库 SQL 核对一致 |
| A3 | 美食城管理 | 删除前校验无档口；上下线影响用户端列表 | 用户端同步 |
| A4 | 入驻审核 | 通过：绑定/创建档口 + 写 merchant_user_id；驳回：必填原因，商家端可见 | 审核后商家端状态同步 |
| A5 | 档口管理 | 抽佣比例 0–30%，精度 0.01；强制下架后不可接单、用户端不展示 | 边界值校验 |
| A6 | 订单监控 | 支持订单号/档口/状态/时间范围；强制取消仅限未完成订单，触发退款退券 | 状态与金额同步 |
| A7 | 平台券 | 发行量、每人限领 1 张、有效期校验（现状已有，补管理端） | 与用户端领券一致 |
| A8 | 秒杀活动 | 同一菜品同一时段不可重叠；库存条件更新防超卖；活动价仅限每人每活动 1 份 | 并发下单不超卖 |
| A9 | 评价处理 | 平台回复与商家回复分开展示；隐藏需填原因，隐藏后不计入评分 | 用户端评分同步 |
| A10 | 结算 | 每日 01:00 生成昨日结算单；退款从结算中扣减；已结算不可改 | 金额可复算 |
| A11 | 系统配置 | 配置项键值对，修改即生效（Redis 缓存 60s） | 改后商家端抽佣生效 |

> 秒杀说明：现有首页"今日抢购"读取 `/dish/hot`（普通热销），并非真秒杀。本期新增 `seckill_activity` 表，用户端按活动价展示，下单时服务端校验活动价与限购，避免"前端特价、后端原价"。

## 四、数据模型变更

### 4.1 新增表

```sql
-- 平台管理员
admin(id, username UNIQUE, password, salt, real_name, role TINYINT COMMENT '1超管 2运营',
      status TINYINT, last_login_time, create_time, update_time, deleted)

-- 商家入驻申请
merchant_apply(id, user_id, shop_name, mall_id, contact, phone, license_img,
               business_hours, status TINYINT COMMENT '0待审 1通过 2驳回',
               reject_reason, audit_admin_id, audit_time, shop_id, create_time, update_time, deleted)

-- 退款单
order_refund(id, refund_no UNIQUE, order_id, payment_id, user_id, shop_id,
             amount, reason, status TINYINT COMMENT '0申请中 1已同意 2已拒绝 3已退款',
             reject_reason, handle_admin_id, handle_time, create_time, update_time, deleted)

-- 结算单
settlement(id, settlement_no UNIQUE, shop_id, period_start, period_end,
           order_count, goods_amount, delivery_amount, discount_amount,
           commission_rate, commission_amount, refund_amount, net_amount,
           status TINYINT COMMENT '0待结算 1已结算', settle_time, create_time, update_time, deleted)

-- 平台配置
platform_config(id, config_key UNIQUE, config_value, remark, create_time, update_time, deleted)

-- 秒杀活动
seckill_activity(id, dish_id, shop_id, seckill_price, start_time, end_time,
                 stock, sold_count, limit_per_user, status TINYINT COMMENT '0下线 1上线',
                 create_time, update_time, deleted)
```

### 4.2 既有表变更

| 表 | 变更 |
|---|---|
| `shop` | `+ announcement`、`+ auto_accept`、`+ commission_rate DECIMAL(5,4) NULL` |
| `order_item` | `+ spec_id`、`+ spec_name`、`+ spec_price` |
| `order_comment` | `+ reply_content`、`+ reply_time`、`+ admin_reply`、`+ hidden` |
| `dish_spec` | `+ sort`、`+ status` |
| `coupon` | `+ creator_type TINYINT '1平台 2商家'`（`shop_id` 为空仍表示平台券） |
| `orders` | `+ accept_time/prepare_time/deliver_time/finish_time/cancel_time`；状态扩展 `6 退款中`、`7 已退款` |

### 4.3 迁移策略（重要）

- 本地库已有数据，**禁止**用 `data.sql` 重建。
- 新增 `docs/sql/migration_v2.sql`：`CREATE TABLE IF NOT EXISTS` + `ALTER TABLE ... ADD COLUMN`（幂等，可重复执行）。
- 同步更新 `docs/sql/schema.sql` 为最终态。
- `data.sql` 仅在末段追加：管理员测试账号、示例入驻申请、示例秒杀活动；并保证可重复执行。

## 七、关键业务流程

### 7.1 商家入驻审核

```text
商家微信登录(role=2, 未绑定) → 提交入驻申请（档口名/美食城/联系人/手机/执照图）
→ 平台审核
   ├─ 通过：新建或选择空档口 → 写 shop.merchant_user_id → 申请状态=1
   └─ 驳回：填写原因 → 申请状态=2 → 商家端展示原因，可重新提交
→ 商家端刷新后进入工作台
```

### 7.2 退款

```text
用户申请退款（订单未完成）→ 生成 order_refund(0)
→ 商家同意：订单 6 退款中 → 模拟退款成功 → 订单 7 已退款、payment=已退款、退券、结算扣减
→ 商家拒绝（原因）→ 退款单 2；用户可申请平台介入（平台强制退款走 A6）
约束：待支付订单直接取消；已完成订单退款需平台审批（本期平台端强制退款）
```

### 7.3 结算

```text
每日 01:00 → 汇总昨日 status=4 的订单（扣除周期内退款）
→ 按档口生成 settlement（抽佣基数=商品金额-平台券分摊）
→ 平台确认打款 → 标记已结算 → 商家端账单可见
```

## 八、风险与边界（开发前评估）

| 风险 | 影响 | 应对 |
|---|---|---|
| 角色由客户端声明 + 自助绑定 | 他人可抢绑空档口 | 本期改为入驻审核；`/auth/login` 仅允许 1/2；绑定只由平台写入 |
| 订单状态扩展 6/7 | 用户端/商家端/统计/15 分钟取消任务均需同步过滤 | 全局搜 `status` 判断，集中常量；自测覆盖 |
| 秒杀并发 | 超卖、价格不一致 | 库存条件更新 `sold_count + n <= stock`；下单服务端重算价格 |
| 退款与结算 | 重复退款、结算多算 | 退款单唯一约束 + 支付/订单条件更新；结算按退款时间扣减 |
| 金额精度 | 分摊尾差 | 沿用现有按比例分摊、尾差归最后一组；统一 BigDecimal |
| admin-web 部署 | 跨域/路径 | 开发 proxy，生产 Nginx 同源反代 |
| 语音提醒 | 无音频文件无法播报 | 缺省震动+提示音降级；你提供 mp3 后启用 |
| 数据库迁移 | 丢失现有数据 | 只执行 `migration_v2.sql`，禁止跑 `data.sql` 重建 |
| 测试数据 | 管理端空数据无法验收 | 追加管理员、入驻申请、秒杀活动、退款样例 |
| 真机验证 | 仅编译通过不等于可用 | 管理端本地起服务逐页点通；两端小程序 `cli preview` + 接口自测 |
